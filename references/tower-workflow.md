# 塔台流程

目标：统筹子代理完成开发和验收，向用户交付一个按用户标准判断可靠的结果。下文 `S=~/.claude/skills/herdr-tower/scripts`。

## 九个步骤

1. **设置检查。** 运行 `bash $S/tower-config.sh list`。没有配置时按 [setup.md](setup.md) 引导。再对要用的 CLI 运行 `bash $S/tower-config.sh check <cli>`，失败就告诉用户。
2. **接收任务。** 明确目标。“可靠”由用户按任务定义：用户没给验收标准时，起草一份，请用户确认后再开工。标准确认后不能自行修改；发现做不到或不合理，先通知用户。
3. **选择审批方式。** 询问一次，默认自动。用户已说明时跳过。选人工时要说明：codex 沙箱内的操作仍不会逐条询问，需要逐项把关的角色应改用 claude 或 grok。
4. **准备现场。** 运行 `bash $S/tower.sh init <任务名>`，它打上 `🗼 塔台` 标签并输出状态目录 `<state>`。任务名不能有空格或 `/`。
5. **制定计划。** 拆分工作、确定依赖和角色，写入 `<state>/progress.md`。默认角色是开发、测试、验证、文档，按任务增减。提前判断哪些步骤涉及危险操作，先问用户。
6. **派发。** 每个子代理都带 `--role <角色> --state-dir <state> --approval <用户选的方式>` 启动，并在后台运行。启动后从输出文件读取 `run=` 和 `pane=`，写进进度文件。
7. **监督。** 等脚本通知，按 `SKILL.md` 的退出码和审批规则处理。每次启动子代理、收到结果或得到用户回答时，先更新进度文件，再做下一步：中断恢复只能依靠它。
8. **验证与修复。** 见下文。
9. **交付。** 先把进度文件更新到最终状态，再运行 `bash $S/tower.sh finish <state>` 恢复标签，再按验收标准逐项报告：通过项及证据、未完成项、你替用户做的决定。证据来自验证者，不来自开发者的自述。

## 任务说明模板

```markdown
## 目标
<一句话>

## 范围
<工作目录、可以改哪些文件、不能碰什么>

## 项目规则
<从项目规则文件摘录与本任务相关的条目>

## 验收标准
<与本任务相关的条目，原文照抄>

## 危险操作
遇到难以撤销的删除或覆盖、改写已推送历史、部署或迁移、对外发布或推送、读取或修改密钥和权限时，
不要执行。在报告里写明你想做什么、为什么，然后结束。

## 提交
不要提交，不要推送。

## 报告
写清做了什么、改了哪些文件、运行了什么命令及其结果、还有什么没做。
```

脚本会自动追加两条：被沙箱或权限挡住时申请批准而不是绕过，以及把最终报告写入结果文件。子代理之间不直接对话，它们需要的信息都由塔台写进任务说明。

需要提交时，只有验收标准或用户明确要求才把“提交”一节改掉。推送一律按高危处理。

## 验证

验证者和开发者必须是不同的子代理。验证者在独立副本里工作，可以安装依赖和运行测试，用户目录里的文件不受影响。Git 项目的副本是 worktree，会运行用户的 `post-checkout` 钩子，也和用户仓库共享分支，所以任务说明要写明不要建分支。下面三条分开执行，要等验证者真正结束（退出码不是 10 或 11）才能 `remove`：

```bash
copy=$(bash $S/verify-copy.sh create <项目目录> <state>)   # 包含未提交和未跟踪的改动
bash $S/pane-agent.sh start --role 验证 --state-dir <state> --approval <用户选的方式> --cwd "$copy" --task "..." --prompt-file ...
bash $S/verify-copy.sh remove "$copy" <state>              # 读完结果后丢弃
```

验证者的任务说明要写：逐项检查验收标准；每项给出“通过 / 不通过”和证据（实际命令及输出）；不要修复问题；不能确认的项写“无法确认”，不能算通过。验证后如果又有改动，要重新创建副本再验证。

## 修复循环

验证不通过时，开一个新的开发子代理（不依赖旧会话），任务说明里写明原任务、当前改动和验证者给出的具体失败证据。修复后重新验证。

在进度文件里按验收项计数：**同一项失败 3 轮后停止，把证据告诉用户**，不要继续尝试，也不要放宽标准。

## 并行

- 同一工作目录同一时间只能有一个有写权限的子代理。
- 验证副本互相独立，可以并行。
- 确实需要并行开发时才用 Git worktree，并由塔台安排合并。
- 布局由脚本处理：右列最多 4 个 pane，超出进入 `🐝 调度 N` tab；当前 tab 已有其他 pane 时，子代理全部放到新 tab。

## 进度文件

路径是 `<state>/progress.md`，这样上下文压缩或中断后还能接着调度：

```markdown
# <任务名>
目标：
工作目录：
审批方式：自动 | 人工

## 验收标准（用户已确认）
- [ ] 1. ...  失败轮次：0

## 子代理
| 角色 | CLI | 模型 | 依赖 | 状态 | pane | 运行目录 | 验证副本 |

## 等待用户确认

## 替用户做的决定
```

## 中断恢复

先读进度文件，再查 `herdr pane list`。

- **上下文压缩后：** 按进度文件继续。
- **塔台进程重启，子代理还在：** 对每个还在运行的子代理，在后台运行 `bash $S/pane-agent.sh watch <run>` 重新接管。这是尽力而为，告诉用户发生过中断。
- **机器重启：** pane 和子代理都没了。只向用户报告进度和未完成项，由用户决定是否继续。
