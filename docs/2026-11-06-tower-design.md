# 塔台（Tower）技能设计

日期：2026-11-06
状态：待用户确认
基于：现有技能 `herdr-pane-agent`（单个子代理在带标签的 pane 中运行）

## 1. 目的

用户把大型开发任务交给主代理后，只需给出目标，最后收到一个可靠的结果。主代理变成“塔台”，只负责调度，不亲自做具体工作。开发、测试、验证、文档更新都交给子代理，不同类型的工作可以用不同的 agent CLI 和模型。herdr 负责展示整个调度现场。

这是一个通用技能，不绑定任何项目，也不包含任何项目专属规则。

## 2. 目标、非目标和反目标

**目标**

- 塔台从接收任务到交付全程调度，平时不打扰用户。
- 不同角色可以使用不同的 agent CLI 和模型。
- 用户在 herdr 中一眼看清每个子代理是谁、在做什么、用什么模型和 CLI。
- 交付时按验收标准逐项给出证据。

**非目标**

- 不替用户安装或登录 agent CLI。
- 不修改用户的 agent CLI 配置文件。
- 子代理之间不直接通信。
- 第一版不实现跨机器调度。

**反目标（即使技术上能跑，出现这些也算失败）**

- 塔台自己动手做开发、测试等具体工作。
- 塔台自行放宽验收标准，或把没通过的项目说成通过。
- 写代码的子代理验收自己的工作。
- 塔台悄悄把不可用的 CLI 换成别的 CLI。
- 用户无法分辨某个 pane 属于哪个子代理、在做什么。

## 3. 用户已确定的决定

| 主题 | 决定 |
|---|---|
| 塔台职责 | 只协调，不做具体任务 |
| 子代理类型 | 不限于 Claude，也可以是 Codex、Pi、Grok 等 |
| 角色与模型设置 | 首次使用时引导设置，用户明确要求时才更新 |
| “可靠”的定义 | 由用户按任务定义，技能不写死标准 |
| 没有验收标准时 | 塔台先起草一份，请用户确认后再开工 |
| 需要用户确认的事 | 清空数据库这类危险操作 |
| 普通审批 | 主代理可以处理；高危操作转给用户；开始工作时可以选择全部人工审批 |
| Claude 权限模式 | 倾向 `auto` |
| 布局 | 左侧塔台一列，右侧 3～4 个 pane 上下排列，超出时新建 tab 并命名 |
| 塔台标签 | 塔台或其他合适的名称 |
| 子代理标签 | `🚀 名字 · 📝 任务 · 🧠 模型 · 🧰 agent CLI` |
| 子代理生命周期 | 子代理结束，pane 随之消失 |
| Codex 做开发 | 接受沙箱内操作不弹审批，靠塔台把关和任务说明约束 |

用户也确认了以下设计方向：子代理之间不直接对话，信息都经过塔台；写代码的子代理不兼任验证；验证不通过时退回修复，有重试上限；塔台把计划和进度写进文件；首次设置时检测已安装的 CLI、按角色询问并保存为全局配置；单个任务可以临时覆盖配置；配置里的 CLI 不可用时先告诉用户。

## 4. 工作流程

1. **设置检查：** 没有配置时运行设置向导（第 5 节）。
2. **接收任务：** 明确目标。如果用户没给验收标准，塔台起草一份并请用户确认。
3. **选择审批方式：** 询问一次，默认自动（第 8 节）。
4. **制定计划：** 拆分工作、确定依赖和角色，写入进度文件。
5. **派发：** 每个子代理得到一份自包含的任务说明。
6. **监督：** 塔台等待脚本通知，处理审批和异常。
7. **验证：** 由不同于开发者的子代理按验收标准逐项检查并给出证据。
8. **修复循环：** 不通过时把问题退回开发子代理，修复后重新验证。同一项失败 3 轮后停止并通知用户。
9. **交付：** 逐项报告通过项、证据和未完成项。

塔台可以阅读子代理的结果和进度文件来做调度决定，但不编写产品代码、不运行测试、不写文档。

验收标准一经确认，塔台不能自行修改。如果发现某项做不到或不合理，必须先通知用户。

## 5. 首次设置

由塔台在对话中引导：

1. 检测已安装的 agent CLI。
2. 逐个做预检，确认能真正启动，不能只看命令是否存在。实测发现过登录缺失、凭证损坏和默认模型不可用这些情况。
3. 按角色询问 CLI 和模型，并给出推荐值。默认角色是开发、测试、验证、文档，用户可以增减。
4. 标出还没有验证过的 CLI。
5. 保存为全局配置，所有项目通用。

配置保存在 `~/.config/herdr-tower/` 下。单个任务可以临时指定其他 CLI 或模型，不改动配置。没指定模型时，标签显示 `🧠 默认`。

## 6. 布局

**第 1 个 tab：**

```
┌───────────────┬──────────────────────────────────────┐
│               │ 🚀 开发 · 📝 … · 🧠 … · 🧰 claude      │
│               ├──────────────────────────────────────┤
│               │ 🚀 测试 · 📝 … · 🧠 … · 🧰 codex       │
│   🗼 塔台      ├──────────────────────────────────────┤
│   宽度占 40%   │ 🚀 验证 · 📝 … · 🧠 … · 🧰 grok        │
│               ├──────────────────────────────────────┤
│               │ 🚀 文档 · 📝 … · 🧠 … · 🧰 pi          │
└───────────────┴──────────────────────────────────────┘
```

**溢出：** 右列最多 4 个 pane。再多时新建 tab，命名为 `🚀 调度 2`、`🚀 调度 3`，以此类推。这些 tab 不含塔台列，也是最多 4 个 pane 上下排列。

**实测结论：**

- `pane split --ratio` 指的是原 pane 所占比例。先以 0.4 向右分出右列，再依次以 0.25、0.3333、0.5 向下拆分，得到 4 个等高 pane。
- 从 pane 往外分，新 pane 在原 pane 的右侧或下方。
- 关闭右列全部 pane 后，塔台 pane 会恢复全宽。

**需要实现时验证：**

- 右列关闭中间某个 pane 后，其余 pane 是否仍然等高；不等高时用 `pane resize` 调整。
- 右列全部 pane 结束后，下一个子代理如何重建右列。
- 溢出 tab 的最后一个 pane 关闭后，tab 是否自动关闭。

## 7. 子代理生命周期

沿用现有技能的机制：pane 里的进程结束，pane 就消失；子代理完成后写结果文件，由监督脚本发送 `/exit`。退出码（0 `done`、10 `blocked`、11 `needs_attention`、12 `aborted`、13 `timeout`）和超时兜底也沿用。

需要改进：

- **保留崩溃证据：** 直接用 `exec` 时，子代理一崩溃，报错就随 pane 消失了。pane 里要跑一个很薄的外壳，记录退出码并保留最后的输出，退出后 pane 仍然立即消失。
  - 不能简单重定向 stderr：实测 `grok` 重定向 stderr 后界面画不出来。`script` 也不能用，见第 14 节。
- **识别卡住：** 登录页和启动确认框都显示为 `idle`，不是 `blocked`。如果一段时间内一直没有进入 `working`，就读屏幕并报告。
- **后台任务误判：** 现有脚本靠屏幕上的 `N shell still running` 判断 Claude 还有后台命令在运行。其他 CLI 是否有类似情况还未验证，需要各自适配。
- **结果文件：** `claude` 和 `codex` 用 `--add-dir` 放行运行目录；`grok` 由脚本回答那一次写入审批（第 14 节）。

## 8. 审批与危险操作

开始工作时询问一次（用户已说明时跳过）：

| 选项 | 行为 |
|---|---|
| 自动（默认） | 塔台处理普通审批，高危操作转给用户 |
| 人工 | 每个审批都转给用户 |

**高危操作包括：** 难以撤销的删除或覆盖（比如清空数据库）；force push 或改写已推送的历史；部署、迁移或改动线上环境和共享基础设施；发布、发送消息、付款等对外操作；读取或修改密钥、凭证和权限设置。判断不了风险时，也按高危处理。

**三层防护：**

1. **塔台把关：** 派发前判断。涉及危险操作的步骤，先问用户。
2. **任务说明约束：** 明确要求子代理遇到危险操作就停下并报告；被沙箱挡住时要申请提权，不能绕过。
3. **CLI 审批和沙箱：** 按第 9 节的实测结果使用。

**诚实的限制：** 这不是硬保证。`claude --permission-mode auto` 自动放行的操作、`codex` 沙箱内的操作、`grok` 视为只读的命令都不会弹审批。用户已接受这一点。

塔台只能选一次性的批准或拒绝，绝不能选择任何“以后都放行”或切换到更宽松模式的选项。绝不使用 `bypassPermissions`、`--always-approve`、`--dangerously-*` 这类参数。

## 9. CLI 适配

每种 CLI 一份适配定义，至少包括：启动命令模板、模型参数、权限参数、读写角色和只读角色的差异、批准和拒绝按键、启动确认框的处理方式、退出方式、预检方式、验证状态。

**实测结果（2026-11-06，claude 2.1.319、codex 0.167.0、grok 1.0.77）：**

| 项目 | claude | codex | grok |
|---|---|---|---|
| 传入初始任务 | 位置参数 | 位置参数 | 位置参数 |
| 模型参数 | `--model` | `-m` | `-m` |
| 读写角色的权限参数 | `--permission-mode auto` | `-a on-request -s workspace-write` | `--permission-mode default --minimal` |
| 退出 | `/exit` | `/exit` | `/exit` |
| 拒绝审批 | `esc` | `esc` | 读屏幕后按 `No, reject` 那一行的序号 |
| 批准审批 | `enter` | `enter` | 读屏幕后按一次性 Yes 那一行的序号 |
| 启动确认框 | 未遇到 | Hooks need review | 新目录的信任询问 |
| 验证状态 | 全流程已验证 | 全流程已验证（无后台任务场景） | 全流程已验证（无后台任务场景） |

**注意事项：**

- `grok` 的审批界面里，选项 1 是“以后全部放行”，`esc` 只切到回滚视图，编号随工具变化（第 14 节）。
- `grok` 全屏界面在矮 pane 里会把审批选项挤掉，必须用 `--minimal`。
- `grok` 的用户配置可能是 `always-approve`，所以必须显式传 `--permission-mode default`。
- `codex` 的 `-a` 只接受 `on-request` 和 `never`。CLI 版本变化很快，第一次探测和后来的版本就不同了，所以参数要在预检时核对，不能假设不变。
- `codex` 任务说明要写明“被沙箱挡住时申请提权并等待批准”。
- `codex` 的 hooks 确认框：是否信任由用户决定。塔台不能替用户选信任，也不能使用 `--dangerously-bypass-hook-trust`。未决定时按 `esc` 跳过（钩子不运行），并告诉用户。
- 目录信任询问：演练发现三种 CLI 都有。统一停下报告，用户同意后由 `trust <run>` 回答（取代原先 grok 自动回答 `y` 的做法）。
- 未验证的 CLI（`pi` 未安装，`hermes` 未测）不能标记为可靠。第一版支持 claude、codex、grok；其他 CLI 在设置向导里标为“未验证”，用户明确要求且实测通过后才加入。

**按角色收紧权限：** 已被第 13 节取代：验证者在独立副本里可写，不再要求只读。

## 10. 进度文件

塔台把计划和进度写进文件，这样即使上下文被压缩或中断，也能接着调度。内容至少包括：目标、验收标准、审批方式、任务列表（角色、CLI、模型、依赖、状态、pane、运行目录）、修复轮次、等待用户确认的事项。

## 11. 技能结构

把现有 `herdr-pane-agent` 重构并改名为 `herdr-tower`。`SKILL.md` 讲塔台流程和判断规则，CLI 差异放在 `references/` 或适配文件中，脚本负责启动、布局和监督。

## 12. 验证要求

- **复用现有测试场景：** 正常完成、批准、拒绝、外部关闭、超时、后台任务、拒绝不安全模式。这些要在 claude、codex、grok 上各跑一遍；哪个 CLI 不适用，要明确说明。
- **布局：** 4 个 pane 等高、中间 pane 关闭后补位、第 5 个子代理进入新 tab、tab 命名和收尾。
- **端到端：** 用一个真实的小开发任务走完开发、测试、验证、文档、修复循环和交付。
- **用户肉眼确认：** 标签、布局和边框。

## 13. 独立检查后用户确定的决定

- **验证权限：** 验证子代理在独立副本（Git worktree 或目录副本）里可写，副本要包含未提交的改动。跑完丢弃，产物和改动不进入用户的工作目录。第 9 节中“验证角色优先只读”的说法作废。
- **简单用法和触发：** 同一个技能保留两种用法。明确要求“塔台”时走完整调度流程；只要求在 pane 里跑子代理时走轻量流程，不要求验收标准。遇到大型任务也不自动接管，必须明确要求才触发。

## 14. 实测后确定的布局规则

- 关闭中间的 pane 后，herdr 不会自动等分；`pane resize --amount` 难以精确控制。
- 所以不做再平衡：新 pane 从右列最高的 pane 以 0.5 拆分。2 个和 4 个 pane 时基本等高，3 个时一高两矮。第 6 节“等高”的要求按此放宽。
- 溢出 tab 的最后一个 pane 关闭后，tab 自动消失。
- 崩溃证据不能用 `script`：实测它会让 herdr 识别不出 agent（`agent_not_found`，状态一直是 `unknown`）。改为外壳 bash 把 CLI 作为子进程运行，CLI 退出后记录退出码，并用 `herdr pane read` 保存屏幕内容，随后 pane 消失。
- 审批按键不能固定：`grok` 的菜单编号随工具变化（按 3 在 Bash 菜单是 No，在 Edit 菜单是 Yes）。必须读屏幕，只选内容正好是一次性 Yes 或 No 的那一行；认不出就交给用户。第 9 节表格中 grok 的“按 3”以此为准。
- `grok` 不用 `--add-dir`（初始提示词会停在输入框不提交），`--allow` 路径规则也不匹配。所以结果文件的写入审批由脚本回答，且只在对话框正好指向本次运行的 `result.md` 时回答。

## 15. 我替你做的决定（可以推翻）

- 塔台标签用 `🗼 塔台`。
- 塔台列宽度占 40%，溢出 tab 不含塔台列，每页最多 4 个 pane。
- 溢出 tab 命名为 `🚀 调度 N`。
- 右列有空位时优先复用第 1 个 tab。
- 同一项验证失败 3 轮后停止并通知用户。
- 技能改名为 `herdr-tower`，配置放在 `~/.config/herdr-tower/`。
- 第一版只支持 claude、codex、grok。
- `grok` 默认用询问模式（`default`）而不是 `auto`，因为 `auto` 遇到危险操作的表现未测。
- 本设计文档放在技能目录下的 `docs/` 里，不放进任何项目仓库。
- **并行写入：** 同一工作目录同一时间只有一个有写权限的子代理；只读子代理可以并行。需要并行开发时才用 Git worktree，并由塔台负责合并安排。
- **提交代码：** 子代理默认不提交、不推送。是否提交由验收标准或用户决定；推送属于对外操作，按高危处理。
- **已有 pane：** 塔台启动时，如果所在 tab 除塔台外已有其他 pane，就不动它们，也不关闭，子代理全部放到新 tab。
- **收尾：** 交付时清除 `🗼 塔台` 标签，恢复原状。
- **运行目录和进度文件：** 都放在 `~/.local/state/herdr-tower/<任务>/`，不写进用户项目，除非用户要求。
- **修复循环：** 退回修复时新开一个子代理，给它自包含的修复说明，内容包括失败项、证据、原任务说明和当前改动。不依赖各 CLI 的 resume，因为都还没测，而且子代理结束时 pane 应该消失。
- **塔台可读范围：** 为了起草验收标准、拆分任务和写说明，塔台可以读项目文件、项目规则和只读 Git 信息（如 `git diff`）。塔台不改项目文件，不运行测试或构建。项目规则中与任务相关的内容要写进任务说明，因为不同 CLI 读取的规则文件可能不同。
- **人工模式：** claude 用 `--permission-mode manual`，grok 用 `--permission-mode default`。codex 的沙箱内操作无法再逐条询问，所以选择人工模式时，向导要明确告知这一点，并提示用户可以把这个角色换成 claude 或 grok。
- **中断恢复：** 支持上下文压缩后继续；塔台进程重启后尽力接管，即读取进度文件，核对 pane 和运行目录，再重新运行 watch。pane 已消失且没有结果时，按 `aborted` 处理。机器重启后不恢复运行中的子代理，只报告状态。
